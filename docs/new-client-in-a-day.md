# A new client in a day

Every client gets **its own manager portal**: its own web address, its own
sign-in, its own look and language, its own database. Two clients never share
a portal, a database or a login. Yet there is only **one product**: every
client runs the same two images (the cloud API and the web portal), and what
makes a portal *theirs* is configuration written by one script.

That is why a new client is a day's work, not a project:

| What the client gets | Where it comes from |
|---|---|
| Their domain, e.g. `manager.theirshop.com` | one DNS record + one line in the edge proxy (written for you) |
| Their name, logo, colours, font, button shape, layout | a *brand pack*: `brand.json` + 3–4 image files |
| Their languages (e.g. English + Spanish) and currency | the brand pack + one flag |
| Their own database, sign-in and store keys | generated by the script, never shared |
| Their stores syncing in | one settings file per store, printed by the script |

Stores are unchanged: each still runs fully on its own, offline, and only
*sends* its sales up to its client's portal when it has internet.

## What runs where

```
                 ┌──────────────── one server ─────────────────┐
  pub.example ──▶│  edge proxy (Caddy, TLS)                     │
  shop.example ─▶│    ├─ pub.example  ─▶ client A: web + api + db │
                 │    └─ shop.example ─▶ client B: web + api + db │
                 └──────────────────────────────────────────────┘
```

* **Edge proxy** — `cloud/infra/docker-compose.proxy.yml`, one per server. It
  owns ports 80/443 and the certificates and routes each hostname to its
  client. Adding a client is a graceful reload; the others never blink.
* **A client** — `cloud/infra/docker-compose.client.yml`, one copy running per
  client (its own compose project, database volume and network). A client can
  later move to a server of its own with the same files.

## The day

### Morning — the brand pack (1–2 hours)

1. Copy an existing pack: `cp -r cloud/web/brands/sagepoppy cloud/web/brands/<id>`.
2. Drop in their images: a round or square mark (`mark-192.png`, `mark-384.png`),
   a favicon (`icon.png`) and, for the split sign-in page, a wide logo (`logo.png`).
3. Edit `brand.json`:
   * `name`, `legalName`, `wordmarkSub` — what the portal and browser tab say;
   * `palette` and `neutral` — their colours (every text colour on its
     background should reach 4.5:1 contrast);
   * `font` — `inter` or `jakarta`; `shape` — corner radii, `9999px` for pill
     buttons, `shadow` or `none` for a flat look;
   * `layout` — `sidebar` (dark side menu) or `topbar` (light top bar);
     `login` — `band` or `split`;
   * `locales` — e.g. `{"default": "en", "available": ["en", "es"]}`
     (English, French and Spanish are built in); `currency` — e.g. `USD`.
4. Check it: `cd cloud/web && npm test && npm run build && npm run test:brands`
   — the last one renders every page under every pack and fails if any page
   names another client.

A pack can also be mounted instead of built in (`--brand-dir`, below): no
image rebuild, handy for a first look.

### Midday — provision the portal (15 minutes)

On the server (or a laptop, with `--local`):

```sh
cloud/infra/new-client.sh <id> manager.theirshop.com \
  --name "Their Shop" --brand <id> \
  --store "main-st=Their Shop — Main St" --store "harbour=Their Shop — Harbour" \
  --zone America/Los_Angeles --currency USD --country US --retail \
  --admin-email owner@theirshop.com \
  --registry <registry> --image-tag <git-sha> \
  --dry-run            # read the plan, then run again without --dry-run and with --up
```

It writes `cloud/infra/clients/<id>/` (settings and generated secrets, owner
read-only), one store settings file per store, and the proxy site; with `--up`
it starts the client and reloads the proxy. It never prints a secret. Re-run
it any time — to add a store, change the name or roll to a new image — and
it keeps every password and key it made before.

Point the DNS record for `manager.theirshop.com` at the server first: the
proxy fetches the certificate on the first visit.

### Afternoon — connect the stores (10 minutes per store)

Each store gets its settings file from `clients/<id>/stores/<store>.env`
(`CLOUD_SYNC_URL`, its own key, its zone). Copy the file to the store — never
paste the key into a chat or a ticket:

* a desktop store: `scripts/demo-point-store.sh <store> --hosted <file> --yes`;
* a tablet: `scripts/tablet-cloud-config.sh --from <file>` (plus `--app <app>`
  for a second brand app on the same tablet).

The store keeps selling throughout; within seconds of connecting it shows as
online in the portal and its sales history follows.

### End of day — hand over

The owner signs in at their address with the admin email and the password
from `clients/<id>/.env` (`ADMIN_PASSWORD`), enrols their authenticator app,
and changes the password. Done.

## Try it on a laptop

`scripts/demo-clients.sh up --stores` runs two clients side by side behind one
local proxy — `http://cpr.localhost:8088` (a Montréal pub group, CAD, French and
English) and `http://sp.localhost:8088` (a California bottle shop, USD, English
and Spanish) — each with demo stores syncing to it.
